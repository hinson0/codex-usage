# Spec: 统一业务缓存与刷新时机

状态：已实现；菜单栏实窗验收通过。日期：2026-11-03。

杨子已指定使用增量实现和测试驱动开发推进本规格。

## Objective

统一额度、重置券详情、重置动态的缓存时效：正常为 10 分钟；任一有效 Codex 额度窗口的剩余额度低于 10% 时，三项统一为 2 分钟。保留后台更新；打开面板只展示现有数据；用户主动点击刷新时强制重查三项数据。

这是一个共同的业务刷新规则，不拆成可独立发布的多个能力。

### 实施前代码核对结果

| 数据或入口 | 当前行为 | 代码位置 |
| --- | --- | --- |
| 额度及券数量 | 启动时读取，正常每 5 分钟更新；5 小时或长期额度剩余低于 10% 时每 2 分钟更新 | `Sources/CodexUsageCore/UsageController.swift:105` |
| 重置券详情 | 本地文件缓存 24 小时，重启保留；读取时发现数量变化、券到期或账号失效会提前失效 | `Sources/CodexUsageCore/CodexAppServerClient.swift:41` |
| 重置动态 | 保留在内存中，距上次尝试不足 5 分钟时跳过请求；失败保留已有内容 | `Sources/CodexUsageCore/UsageController.swift:138` |
| 打开面板 | 触发业务刷新，并额外检查软件更新 | `Sources/CodexUsageApp/UsagePopoverView.swift:41` |
| 刷新按钮 | 重查额度及券数量，强制获取动态；券详情仍可能命中缓存 | `Sources/CodexUsageApp/UsagePopoverView.swift:54` |
| 软件更新 | 有独立的后台更新信息检查，当前自定义间隔为 5 小时 | `Sources/CodexUsageApp/UpdateCoordinator.swift:50` |

以上以当前源码为准，不能把旧规格中的刷新周期或重置券消费功能当作现行要求。

### 已确认的用户选择

- 保留后台定时刷新，正常 10 分钟、低额度时 2 分钟。
- 取消打开面板时的刷新。
- 点击右上角刷新按钮时，立即绕过三项业务缓存。

### 本规格的范围假设

- “所有缓存”指上述三项业务数据，软件更新检查、语言和外观偏好保持独立。
- 保留现有存储范围：券详情继续落盘；额度快照和重置动态仍只保留在内存中。本次不新增其他数据落盘。
- 首次启动时仍允许一次普通初始化读取；初始化不等于强制绕过有效的券详情缓存。

## 行为要求

### 统一时效

1. 正常时效为 600 秒，低额度时效为 120 秒。后台调度和各项缓存必须采用同一规则，不能继续各自硬编码 5 分钟、24 小时等业务时效。
2. 只检查当前 `codex` 桶的 5 小时和长期额度窗口。任一有效窗口的剩余百分比严格小于 10 时进入低额度模式；恰好 10% 使用正常模式。
3. 根据原始有效百分比判断，不根据界面四舍五入后的整数判断。例如实际剩余 9.9% 即使显示成 10%，也使用 120 秒。
4. 缺少的窗口、无限制的 5 小时窗口及非有限数值不按 0% 处理。所有窗口均未知时先使用正常模式；辅助桶不参与判断。
5. 根据最近一次成功读取的额度重新判断模式。读到恢复至至少 10% 的额度后，恢复 600 秒模式。
6. 缓存年龄从该项数据上次成功获取时间起算；年龄达到当前时效即过期。读取缓存、打开面板、重启应用和请求失败均不得续期。
7. 模式变化作用于现有缓存年龄。当本轮额度读到低于 10%，已有 3 分钟的券详情或动态须在本轮按 120 秒规则刷新，不能再多等一轮。
8. 不同层的缓存不得叠加出更长的实际更新间隔。例如低额度时不能因为保留旧的动态节流而变成每 6 分钟才更新动态。

### 刷新入口

| 入口 | 行为 |
| --- | --- |
| 应用首次启动 | 启动唯一一套后台监控并初始化数据；可复用仍有效的本地券详情。获得新额度后重新判断本轮缓存有效期 |
| 后台到期 | 依据当前 600/120 秒规则更新到期数据；尚有效的数据可复用 |
| 打开、关闭、再次打开面板 | 只显示当前状态，不发起三项业务请求，不额外触发软件版本检查，不重置后台计时 |
| 点击刷新按钮 | 立即重查额度、券数量与券详情、重置动态，不受当前缓存时效或自动重试等待时间限制 |
| 时间文字更新 | 额度恢复日期、准确时间和倒计时继续按本地时间更新，不因此触发网络请求 |

手动刷新成功后，各项成功获取时间随真实结果更新，后续自动调度遵守新的有效期，不因旧的后台唤醒时间立即重复请求。刷新未结束时不启动第二轮重叠请求。反复开关面板不能重复启动后台监控或制造额外初始化请求。

后台轮询不是实时推送：额度在两次读取之间下降，只能在下一次成功读取后被识别；手动刷新可以主动提前读取。

### 重启、提前失效和失败

- 券详情继续使用现有本地缓存文件及原始获取时间。升级后，旧版 24 小时缓存也按新的 600/120 秒时效重新判断，不能保留旧时效或重新计时。
- 券数量发生变化时，不等缓存期结束便核对详情并更新本地缓存；数量变为零时立即移除旧的有效券详情，无须为零张券额外查询详情。
- 继续处理已知券到期、账号变更通知和登录失效造成的提前失效。券数量变化通过下一次额度读取发现，不承诺收到专用的实时用券通知。
- 只获得券数量、没有可用详情时，不编造到期时间；有券但无法确认最早到期时间时显示“时间未知”。不把未成功获得详情视为详情缓存已更新。
- 暂时断网或请求超时时，保留可展示的旧数据及既有错误提示，不刷新成功时间；自动重试仍遵守当前 600/120 秒节奏，禁止紧密重试。认证失效仍清除账户数据和对应券缓存。
- 重置动态是独立公开信息；账户读取失败不能阻止动态按规则刷新，动态失败也不能阻止额度更新。
- 动态请求到期或被用户强制刷新时，不能因为额外的本地 HTTP 缓存而继续使用超过本规格时效的数据。

## Code Style

沿用四空格缩进、类型名 UpperCamelCase、方法与属性名 lowerCamelCase。判断使用业务数据，避免依赖显示文字或真实等待。

以下是当前代码中用于识别低额度的实际写法，说明需要保留的有效窗口语义：

```swift
let hasLowAllowance = [windows.fiveHour, windows.longer].contains { window in
    guard let usedPercent = window?.usedPercent, usedPercent.isFinite else { return false }
    return 100 - usedPercent < 10
}
```

测试继续通过服务接口和可控时间验证结果，使用 `@Test` / `#expect`，避免直接测试私有方法或等待真实的 2/10 分钟。

## Testing Strategy

| 场景 | 必须验证的结果 |
| --- | --- |
| 额度正常、恰好剩余 10% | 三项统一使用 600 秒 |
| 5 小时或长期额度剩余 9.9%、0% | 三项统一使用 120 秒；五小时无限制时仍根据长期窗口判断 |
| 辅助桶低额度、窗口缺失或值无效 | 辅助桶不改变模式；未知窗口不制造低额度 |
| 时效边界 | 599/600 秒、119/120 秒分别命中/过期；命中缓存不续期 |
| 正常与低额度来回切换 | 当次新的额度决定各缓存有效性，不延迟一轮，恢复时重新采用正常时效 |
| 应用重建及旧缓存迁移 | 券详情从本地恢复，保持原始获取时间，按新时效判断 |
| 券数量增加、减少、变为零 | 当前轮次更新或清空旧详情，结果在下次重启后也一致 |
| 反复开关面板 | 业务服务读取次数不增加，不增加更新信息检查，不重置后台计时 |
| 用户点击刷新 | 即使缓存尚有效，也重新读取三项；快速连点不并行执行两轮 |
| 手动刷新后的后台调度 | 有效期内不因为原来的自动唤醒时间重复读取 |
| 失败与恢复 | 保留旧结果及错误语义，不续期、不紧密重试，后续成功可以恢复；动态与账户读取互不阻塞 |

以聚焦单元测试验证上述行为，以现有原生面板交互辅助程序验证打开面板不触发网络请求。完整测试、只读联调、构建、打包、签名及启动检查沿用 AGENTS.md；不新增未经约定的覆盖率百分比门槛。

## Boundaries

- Always：统一三项业务时效；保留券详情本地缓存和原始获取时间；保留提前失效、错误提示及串行刷新行为；遵守当前 AGENTS.md 的额度、券到期时间和实时倒计时显示规则。
- Ask first：扩大到其他数据落盘、修改 Sparkle 更新策略、引入依赖、改变公开动态来源或 CI 配置。这些不是统一业务缓存时效的必要部分。
- Never：消费重置券、记录重置尝试历史、读取或保存令牌及账号/重置券标识、编造到期时间、通过跳过或删除失败检查降低验证要求。
- 实施阶段不改变已发布产物；后续需要发布新 App 时，按 AGENTS.md 为整个改动一次性升级版本。本规格不自动授权新的提交、推送或发布。

## Success Criteria

1. 三项业务数据共同遵守 600/120 秒规则，严格使用“剩余低于 10%”作为切换条件。
2. 后台刷新保留；打开面板零新增网络请求；只有明确点击刷新按钮才强制绕过所有业务缓存。
3. 本地券缓存重启后保留但不续期，旧版 24 小时缓存不能绕过新时效；数量变化仍能提前刷新。
4. 所有时效与入口行为均有可重复的验收证据；产品显示、错误处理及软件更新独立性保持满足仓库约束。
5. 按用户指定的增量实现和测试驱动流程验证每个行为切片。
